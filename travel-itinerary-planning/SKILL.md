# 🗺 行程规划与可行性验证

> **分工**：`trip-advisor`（第三方技能）管**数据查询**——车次/酒店/景点怎么查；
> `travel-guide`（第三方技能）管**文档生成**——itin.json 怎么变成 Word/Excel；
> **本技能管中间那段最要命的活**：路线怎么设计、时间够不够、图怎么画。

## 何时用

- 用户给出目的地 + 天数 + 成员，要一份能落地的行程
- 用户自己排了顺序，问"这样行不行 / 验证可行性"  ← **触发本技能的量化验证流程**
- 用户要"手绘路线图 / 行程图"

## 环境前置（本机已具备，新环境先验）

```powershell
flyai --help                       # 飞猪 CLI：车次/酒店/景点实时数据
python -c "import docx, openpyxl, matplotlib; print('ok')"   # 文档+绘图
```

## 六步工作流

### Step 1 · 先查档案，再开口问

**用户已明确纠正过**："你知道我孩子多大的啊"——凡家庭成员、既往偏好、证件情况等，
**先 `memory_search` 再问**。只问档案里没有的信息。

一次把所有待确认项列全（分「必须你拍板」「不答我按默认走」两组），别挤牙膏式来回问。
必须先问清的：**返程日期**（决定抢票日）、**成员构成与年龄**（决定门票档位/体力安排）、
**是否已订票**（避免重排）、**酒店档次与房型**。

### Step 2 · 数据全部实测，禁止估算

| 数据 | 工具 | 铁律 |
|---|---|---|
| 车次时刻 | `flyai search-train` | **必须用车站名**（目的地站/郑州东/洛阳龙门），用城市名会被普速车淹没；飞猪每次只返回 10 条，用 `--dep-hour-start/--dep-hour-end` 限定时段补查 |
| 酒店 | `flyai search-hotel` | 用 `--poi-name` 按景点筛、`--hotel-bed-types '双床房'` 按房型筛 |
| 景点 | `flyai search-poi` | **重点看 `listRank` 榜单排名**（如"洛阳亲子景点榜第2名"）——这是判断适不适合带孩子的硬信号 |
| 距离/车程 | web 搜索 | **不能拍脑袋**。本技能就是靠这一步抓出两处估算错误（见坑 #2） |

📖 **动手查数据前先读 `references/flyai-data-source-notes.md`**——车站名 vs 城市名的坑、
时段/房型参数用法、返回结构速查、PowerShell 调用坑都在那里。

⚠️ 飞猪**体验模式**下机票价格精确，但酒店/火车/门票价格打码（`¥1xx`）。**不得把打码价格当真实报价输出**。

### Step 3 · 路线设计四原则

1. **票源多的方向放结尾**：返程票最难抢，把"车次最多的枢纽"放在最后一站。
   实测对比：郑州→长沙 8+ 趟 / 洛阳→长沙 6 趟 / 开封→长沙 2 趟 → **从郑州或洛阳回，不从开封回**。
2. **"死胡同"放开头**：末尾站是没有其他方向可走的地方（如开封在郑州以东），
   万一没票就滞留。放开头则去程票可以从多个方案里选。
3. **靠夜场的景点必须占整天**：
   - 万岁山（打铁花夜场）、清明上河园（《大宋·东京梦华》）→ 各需 1 整天
   - 只有河南（09:00-22:00，7 个室外剧场全是夜场）→ 需 1 整天
   - **识别方法**：查营业时间 + 问"招牌演出在白天还是晚上"。放最后一天会跟返程撞车。
4. **顺路的移动日合并**：景点夹在两城之间时（如少林寺在郑州—洛阳之间），
   安排在"从 A 城退房去 B 城"的当天，行李放包车后备箱，不回头。

时间不够时，**明确告诉用户必须牺牲哪一个**（"要么 A 缩水、要么 B 砍掉"），别假装都塞得下。

### Step 3.5 · 给既有行程插可选项目（游船 / 演出 / 加餐）

用户拿着已定行程问「XX 放哪天合适」时，**不要直接甩一个推荐**，按这个顺序来：

1. **先列候选时段表**：`候选时段 | 可行性 | 卡在哪`——把每天的每个可用缝都摆出来（D3晚 / D4早 / D4晚 / D5早…）。
   用户要的是「比较」，不是一个答案。
2. **先钉死硬约束，再谈喜好**：招牌演出的固定场次（万岁山打铁花 ≈19:30 / 21:00，只此两场）、
   末班与停止登船时间（汴河游船末班 21:30）、闭园/停止入园、退房出发与赶车时间。
   只有落在硬约束之间的缝才是候选，其余是幻觉。
3. **算「顺路成本」而不是「距离」**：加项优先放在**已有景点的门口**。
   实例：汴河游船的清园翰园码头就在清明上河园迎宾门马路对面 → 出园 2 分钟上船、零打车，
   而且能并进门票联票里 → 边缘成本近乎为零。这类项目**不占整天、只吃傍晚**，优先级最高。
4. **塞进「节奏最松的那天」**：连日赶行程里，把可选项放进本来就闲的那天（本例 D4），
   而不是放进已经「早起 + 两万步」的那天（D3 万岁山）。
5. **顺手算联票**：加项若并入了既有门票的联票（万岁山 + 汴河游船 **128 元** vs 单买 100 + 60 = 160 元），
   写清「多花 X 元多得 Y」，比单报加项票价有说服力。
6. **约束一变就重排，别打补丁**：用户做减法（如「不看《东京梦华》」）等于腾出一整块晚上 →
   重跑一遍候选时段表，不要在旧方案上缝补。



### Step 3.6 · 换/加某天的落点（「D5 不去 X 了，改去 Y」）

**先分档再推荐**：用户问「除了 X 还有什么地方推荐去」时，别按名气排——**按「从当前出发点出发的可行性
（车程/要不要过夜）× 对返程站与住宿的连带影响」分档**，并**主动点出返程站约束**（"D6 从哪个站走？"）。
用户要的是能落地的候选，不是一张景点榜单。（本次把"郑州·河南博物院"排在第一档的理由就是：
离返程枢纽近 + 室内 + 免费 + 正好是被砍掉的原亮点。）

**定了新落点之后，这一天换了会连带 6 项，别只重排那一天**：

1. **车票**：同一趟车常能换区段用 —— 本次 `G2207 开封北 09:54` 既到洛阳龙门也到郑州东
   → 改买**新区段**（`开封北→郑州东` 10:15 到），**旧区段别再买**。未开售的更新「待买清单」、
   已买错的退票。先算开售日（预售 15 天含当日：10/5 的票 9/21 开售、10/6 的 9/22）
   → `references/ticket-booking-playbook.md`
2. **被砍景点的票要退**：龙门石窟未使用门票在**出游当日 20:00 前退不计爽约**，超时算 1 次，
   爽约 3 次禁约 180 天 → 把「要退的票」列成待办交给用户，别默认他没订
3. **住宿**：换城市 = 退旧订 + 订新；「住宿待定」的落点描述也要改
4. **返程站可能被动改变 → 必须重查，别假设变差**：本次返程由洛阳龙门改郑州东，实测
   **郑州东→目的地站 G311 13:37→16:25 = 2h48m**，比原 *洛阳龙门→目的地站 G406 13:42→17:19 的 3h37m*
   **快 49 分钟** —— 正好印证 Step 3 原则 1「票源多的方向放结尾」
5. **下游那天要重排**：D5 换成下午在场馆内，D6 上午就从"洛阳白马寺"变成"郑州机动" ——
   别让下一天还留着前一城市的景点
6. **三处载体同步**：手账图 HTML→PNG、`itin.json`、变更记进 `notes` 留痕。
   ⚠️ **`itin.json` 最容易漏**——它不显眼，但下次读它就会拿到旧城市（某日 正是因此翻车）。
   Word/xlsx/PDF 若在冻结期，**在对话里明说"只同步了图与 itin.json，交付物仍冻结"**，别静默

**收尾方式**：列「**必须你定的 N 件事**」（本次：D5 住哪个片区 / D6 上午怎么安排+坐哪趟 /
hero 配图要不要换），别自己拍板闭环。

### Step 4 · 时间链量化验证（本技能核心）

把每天拆成时间点，逐段算「可用间隔 vs 最小所需时间」。用
`scripts/verify_timeline.py`（输入 JSON，输出可行性矩阵 + 每日游玩时长）。

判定标准：
- 可用 ≥ 需要 + 15 分 → ✅ 充裕
- 需要 ≤ 可用 < 需要 + 15 分 → ⚠️ 偏紧（**建议提前 15-20 分钟出发**）
- 可用 < 需要 → ❌ 必须调整

**硬要求（来自实战）**：
- 同站换乘 ≥ 40 分钟（大站如郑州东，走中转换乘通道不出站）
- 赶高铁当天，从市区到车站要按 **打车时长 + 进站 15 分钟** 算
- 国庆/黄金周所有缓冲再上浮 15 分钟

### Step 5 · 手绘路线图（`scripts/draw_route_map.py`）

用 matplotlib 的 `path.sketch` 手绘抖动内核 + 楷体，**不依赖任何生图模型**。
输入 JSON（城市节点 + 箭头 + 日程条），输出 PNG。

**画完必须过布局自检**：

```powershell
python scripts/check_text_overlap.py <你的绘图脚本.py>
```

它用渲染器取出每个文字的真实包围盒做碰撞检测——第一版通常有重叠（实战中查出 4 处，
最大 28848px² 是节点标签被箭头标签压住），**调到输出 `✅ 无重叠` 再交付**。

### Step 6 · 交付

- Word：`travel-guide` 的 `gen_docx.py`；手绘图先转成 `<工作目录>/.temp/map_<目的地拼音>.jpg` 再跑，图会自动插进"出行概览"之后
- Excel：`gen_xlsx.py`（13 列，含具体酒店名/餐厅名）
- **原图直接 `MEDIA:<png路径>` 发给用户**（可转发家人群）
- 交付前 `read_file` 读一次 docx/xlsx 验证内容真写进去了

## 常见坑（全部实踩）

1. **查高铁用城市名会漏车**：查「洛阳→开封」只见普速夜车（2h+），改查「洛阳龙门→开封北」
   才发现 7 趟直达高铁、仅 1h03m。**车站名 ≠ 城市名**。
2. **距离/车程靠估会错**：实战中我把"洛阳龙门站→龙门石窟"估成 4-5km/10 分钟，
   实际 **6.6-6.9km/12-20 分钟**；把"开封北站→清明上河园"估成 20 分钟，
   实际 **约 15km/25-30 分钟**。**改一个数字就要重算整天的时间链**。
3. **车站名对不上城市属地**：少林寺在登封，**没有铁路客运站**（实测"郑州→登封""洛阳→登封"均无班次），
   只能公路。规划前先验"目的地有没有火车站"。
4. **国庆/黄金周的预约不可改**：清明上河园、万岁山需提前一天报备，**预约后不可修改日期**，
   务必让用户看清再提交。龙门石窟、只有河南（主剧场次买票即定）同理。
5. **儿童票凭身份证**：6-14 岁买儿童票要身份证，没办证会卡在 12306"添加乘车人"这一步——
   抢票前必须提醒。
6. **行李转移日**：退房→玩→换城市的那天，**建议包车**（行李全程放后备箱），
   否则拖 4 人行李转公共交通会崩。
7. **门票档位口径各景区不同（年龄 vs 身高），必须逐个查**：龙门石窟是「**12 周岁（含）以下免票**」（按年龄），万岁山 / 清明上河园是「**1.2m 以下免票**」（按身高）——一刀切必错。
   📖 完整口径表 + 「买到儿童票即反推孩子超过身高线、进而校正其他景区费用」的交叉推断技巧 → `references/ticket-booking-playbook.md`
   报价前先算 2 大 2 小的实际门票总额，别只报成人价。

8. **节假日的门票有效期会缩水，「出园再回园」的排法会凭空失效**：清明上河园、万岁山平日是
   「3 日内不限次游玩」，但**五一、国庆等超高峰假期会临时改为「单日单次」**
   （万岁山 2025 国庆即「100 元玩 1 天」，直到 10 月 6 日才恢复 3 日制；清明上河园五一 5/1–5/3 同办）。
   → 凡「白天出园玩个加项、再回园看夜场」的排法，**节假日默认不成立**；
   节假日里可选项只能塞在**进园前**或**出园后**。查有效期时顺手推演它对排程的后果，别只记数字。

9. **「三日有效」≠「当日可多次进出」**：多日有效票通常含义是「**每天可进一次**」。
   凡排了「出园玩加项 → 再回园看夜场」的（如出园坐船 → 回园看打铁花），
   **交付前先确认门票允许当日二次入园**；拿不准就把顺序改成「**园内玩透 → 出园后做收尾活动**」，
   全程不回园 —— 这样无论票是哪种规则都成立。
10. **火车票掐点、景区票等放号，别混为一谈**：12306 是 **15 天预售（含当日）**，
    起售钟点**按乘车站**各不同（10/5 的票 9/21 开售、10/6 的 9/22）；
    景区票**各店自定**、长假一般提前约 7 天放号，且**龙门石窟假期必约满**
    （2026 清明 4/4、五一 5/2–5/4 均有官方「预约已满」公告）。
    用户说「现在还买不了」时，先分清是哪一类，再给时间表 → `references/ticket-booking-playbook.md`
11. **票务状态写错，比数字写错更坑**：图上写「已提前预约」之前先确认真买了；未定时用**中性表述**
    （"实名分时预约"），买了再改成"已购票"。改票务信息要**同步所有列了费用的载体**
    （手账图 HTML → PNG、itin.json 底稿），改完 grep 回读核对。
12. **「周一闭馆」是排程高频杀手，长假例外要逐个查**：某日 实况——D5 落在 **10/5 周一**，
    而河南博物院常规是「**周一闭馆（法定节假日除外）**」，10/5 在国庆假期内 → **正常开馆**。
    **差一点就排出一个闭馆日**。→ 凡排到周一：先查该场馆官方口径（博物馆/纪念馆/美术馆几乎都周一闭馆），
    并**确认"法定节假日除外"是否覆盖当天**；用户能约到票本身就是开放证据。
    ⚠️ 反方向也要防：馆方在长假**调整开闭馆日**（如"9/28、9/29 闭馆维护"），以官方公众号当期公告为准。
13. **改行程时最容易漏掉的是"没人记得要改的那个文件"**：交付物（Word/PDF/图）用户天天看，
    反而**内部源数据（itin.json 之类）没人盯**——而下次开工读的正是它。
    某日 就因为读了未同步的旧行程数据，得出"龙门石窟在 D1"的结论被当场打回。
    → **换行程后，把 itin.json 当成交付物一起同步，并在回复里报一句"已同步"**。
    载体权威顺序（手账图 > 其它文件）见 `travel-fact-verification`。

## 输出风格（用户偏好）

- 表格优先，结论先行，**数据敏感**——每个数字标明来源（实测 / 网络参考 / 需核实）
- 分析结果**直接展示在对话里**，不要只写进文件让用户去翻
- 诚实交底局限：哪些是实测、哪些是估算、哪些必须在 12306/景区官方复核
- 用户会主动纠正错误（"洛阳龙门到开封有高铁啊"）→ **立刻承认 + 重拆数据，不辩解**
